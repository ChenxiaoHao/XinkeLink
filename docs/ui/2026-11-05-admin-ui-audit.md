# 信科 Link 管理后台界面审查与五天上线优化建议

日期：2026-11-05。范围：管理员登录、十个后台业务主页面及关键抽屉、空状态和确认弹窗。使用 Product Design 的截图审查流程与 taste-skill 的 app-screen 规则。

**结论：后台已有可延续的公共布局，不建议上线前推倒重做。当前优先级是修正错误数据与操作提示，然后统一可读性和操作区；不能将这次界面检查视为生产上线验收。**

## 1. 本轮实际做了什么

- 使用本机 Chrome，1440×900，连接当前项目的真实本地 Java 服务与既有开发 MySQL，没有拦截或伪造接口响应。
- 新截图共 22 张：11 个主页面、8 个详情／编辑抽屉、设置下半页、帖子无结果状态、设置恢复确认弹窗。均已打开检查。
- 验证只读搜索、打开／关闭抽屉、菜单导航和独立滚动；未删除、隐藏、发布、发送通知、封禁用户或保存设置。
- 抓取记录包含 140 次 API 响应，没有 HTTP 4xx/5xx 或浏览器未捕获异常；这是临时检查环境中的访问记录，**不是 140 个接口或 140 项业务测试**。POST 仅含管理员登录及不写业务数据的通知受众预览。
- 11 个主页面没有浏览器整页横向溢出，截图中的图片均加载成功。设置页滚动时顶栏、侧栏位置不变，window.scrollY 为 0。
- `apps/admin` 审查前后文件哈希一致。本轮没有修改小程序、后台或 Java 产品代码，没有运行迁移、全量测试或生产构建，没有 Git 提交。

### 环境限制和本轮处理

原有 18081 服务对标准后台来源 `https://localhost:5173` 的管理员登录返回 403/FORBIDDEN。初次 HTTP 地址同样不能登录。后续显式指定可信来源，在 **18084 后端＋5174 HTTPS 预览**启动临时检查进程后，同一后端包、既有账号和数据库可以正常登录。

因此可确定当前运行环境存在后台来源／启动配置问题；原进程的环境内容没有被读取，**“可信来源缺失或不匹配”是基于对比结果的定位方向**。不能归因于密码错误，也没有关闭权限校验。临时进程禁用了 Flyway，没有替换原 18081 服务。该临时环境的页面截图不能证明原启动方式已修复。

## 2. 上线前优先修复的四项 P1

### P1-01：当前常规启动环境不能正常登录后台

- **证据**：上面的真实 403 响应及临时环境对比。登录画面见第 1 页。
- **影响**：部署或重启后，管理员可能完全无法进入后台。
- **建议**：统一 HTTPS 后台地址、服务端可信来源和启动说明；按实际部署域名配置，保留来源校验。用正常启动方式复验登录、刷新恢复、退出，不能只用临时环境通过替代。
- **预计范围**：启动环境、部署说明；优先不改认证业务。约 0.25–0.5 人日，取决于环境排查结果。

### P1-02：帖子列表展示了人为增加的浏览量

- **证据**：截图 03 首条显示眼睛图标＋121；截图 12 同一帖详情为 1 次点赞、浏览量“暂未采集”。`apps/admin/src/views/PostManagementView.vue:155` 实际为 `row.likes + 120`。
- **预期**：只有真实采集的浏览量才能显示数字；没有数据时显示“—／未采集”。点赞使用心形和真实点赞数。
- **建议**：移除加 120 的展示逻辑；列表与详情采用同一互动字段与图标，不擅自补造浏览统计。
- **预计范围**：帖子列表、相关展示测试。约 0.25 人日。

### P1-03：用户列表把尚未加载的发布数量展示成真实 0

- **证据**：截图 07 五位用户的帖子／评论／商品数全为 0；打开首位用户档案后，截图 16 为帖子 1、评论 1。只读复现：打开前 `000`，打开后 `110`，其他用户仍为 `000`。
- **原因**：`UserManagementView.vue:143` 读取 `store.userActivity(row.id)`；`content-moderation.ts:86` 在未加载档案时返回空数组，实际内容到 `loadUserDetail` 才请求。
- **预期**：进入列表就显示可信数量；未获取的值显示“—”，不能冒充 0。
- **建议**：优先使用服务端列表聚合计数；若契约暂不支持，先显示“查看档案”或未加载标识。不要为每行逐个加载全部内容来凑数量，避免 N+1 请求。
- **预计范围**：用户列表／适配层，必要时补现有列表计数字段。约 0.5 人日。

### P1-04：通知发送的风险说明互相矛盾

- **证据**：截图 18 顶部说明“真实站内通知”，底部却说“点击确认后不会触达微信用户或其他真实接收方”。`NotificationManagementView.vue:148` 保留了这句演示文案；实际 Store 调用 `/notifications/{id}/send`。
- **影响**：管理员可能误认为是在演示而对真实站内用户群发送不可撤回通知。
- **建议**：统一为“将向所选用户发送真实站内通知，不调用微信订阅消息；发送后不可撤回”。确认步骤清楚显示标题、范围、当前人数及人数变化提示。历史通知的接收人数应保留发送时快照，不能硬改成当前用户总数。
- **预计范围**：通知编辑抽屉、发送确认文案与相关测试。约 0.25 人日。

## 4. 跨页面统一方案（P2，控制修改范围）

1. **文字与颜色**：主文字采用现有深色 `#202C3E`，辅助文字用 `#667085`；保留 `#6489B8` 用于主要操作／选中，避免整张表的文字都呈蓝灰色。表格正文与输入文字建议 14px，次要字段 12–13px，页面标题 22–24px，数值 26–28px。实测设置说明是 12px、`#8A95A5`，对白色对比度约 3.03:1，不足以支撑这种小字。不是要求所有小字都加粗。
2. **统计区**：复用现有统计组件，降低每页四张卡的高度，减少“服务器数据”“全局有效记录”等重复说明，允许统一成一个带细分隔线的统计条。不要在五天内同时重写所有页面布局。
3. **表格与间距**：筛选栏控制高 36–40px，控件间距 8–12px；纯文字行约 48–56px，带头像／两行信息约 72–88px，正文真正多时再自然增高。金额和可比较数字右对齐，状态使用文字和颜色双重区分。
4. **图标与点击**：现有 Lucide 系统可保留，无需更换库。统一列表操作图形约 16px、点击区至少 32×32px，普通动作雾蓝／中性，删除／封禁红色；图标有 tooltip 和可访问名称。不要为了“惊艳”给管理表格加弹跳、发光或整页进场动画。
5. **抽屉与反馈**：统一标题／对象标识／内容／底部操作四层；长内容局部滚动，底部操作清楚可达。危险动作保留确认与原因，不将“查看”和“删除”设计得难以区分。失败信息就近展示并可重试，避免只有全局 Toast 后无法理解。

这些建议来自本次截图、DOM尺寸和源码；并非完整无障碍认证。键盘遍历、读屏和全站错误注入仍需专门验证。
