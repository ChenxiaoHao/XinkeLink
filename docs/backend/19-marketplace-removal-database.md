## 验证与执行说明

使用项目已有 Flyway 12.4.0 与独立迁移账号实际运行。首次尝试在第一条 `CREATE TEMPORARY TABLE` 处因迁移账号没有该权限失败，未执行任何业务清理。核对失败位置和权限后，改用迁移账号已有 CREATE/DROP 权限支持的普通辅助表；通过标准 Flyway `repair()` 清除失败历史，再执行迁移。五张辅助表全部在迁移结束时删除，没有增加账号权限。

审阅发现旧商品评论的回复可能指向同级回复，按物理顺序删除可能触发 RESTRICT。V9 在删除前仅将待删除商品评论的 root/reply 两列同时置空，满足原有层级约束；论坛评论不受影响。在尚未发布的本地 V9 上完成该修订，经主任务授权使用 Flyway `repair()` 对齐校验和。没有使用手写 SQL 修改迁移历史，V1–V8 校验和保持不变。

- 将执行前完整备份恢复到本轮独立测试库，额外插入商品根评论、一级回复和指向该回复的同级回复，真实 V9 迁移成功；三个商品评论被删除，四个原论坛评论及上述受保护数据哈希保持一致。
- 当前开发库最终 V9 校验和 `-960317247`，V1–V9 均成功，Flyway `validate()` 成功，再次 `migrate()` 执行数为 0。
- 当前库业务表 25 张；迁移辅助表 0 张；`product%` 列 0 个；含 product/market/sellers 的检查约束 0 个；悬空图片绑定 0 条。
